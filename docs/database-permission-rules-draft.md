# 云数据库权限规则草案

当前项目主要通过 `campusApi` 云函数控制权限。正式上线前，云数据库建议收紧为“前端尽量只读公开数据，写操作走云函数”。

## 建议策略

- `users`：用户只能读写自己的基础资料；角色、认证状态只能由云函数改。
- `posts`：前端可读 `status = published` 的帖子；发布、下架、审核走云函数。
- `comments`：前端可读已发布评论；新增和审核走云函数。
- `orders`：用户只能读自己的订单；订单状态变更走云函数。
- `messages`：用户只能读写自己的消息。
- `addresses`：用户只能读写自己的地址。
- `merchants`、`products`、`announcements`、`coupons`：前端只读；新增/编辑走云函数。
- `reports`、`verification_requests`：用户只可新增自己的申请或举报；管理员查询和处理走云函数。
- `admin_logs`：只允许管理员读取；所有写入都走云函数。

## 推荐上线权限形态

| 集合 | 前端读 | 前端写 | 写操作方式 |
| --- | --- | --- | --- |
| `users` | 仅本人 | 仅本人基础资料 | 角色/认证走云函数 |
| `posts` | 公开已发布 | 不直接写 | 发布/审核走云函数 |
| `comments` | 公开已发布 | 不直接写 | 评论/审核走云函数 |
| `orders` | 仅本人 | 不直接写 | 下单/状态走云函数 |
| `messages` | 仅本人 | 仅本人已读状态 | 系统消息走云函数 |
| `addresses` | 仅本人 | 仅本人 | 云函数或前端本人写 |
| `merchants` | 公开读 | 不允许 | 管理后台云函数 |
| `products` | 公开读 | 不允许 | 管理后台云函数 |
| `announcements` | 公开读 | 不允许 | 管理后台云函数 |
| `reports` | 不公开 | 仅新增本人举报 | 云函数 |
| `verification_requests` | 仅本人/管理员 | 仅新增本人申请 | 云函数 |
| `admin_logs` | 管理员 | 不允许前端写 | 云函数 |

## 上线前必须避免

- 不要把所有集合设置为“所有用户可读写”。
- 不要允许前端直接修改 `users.role`。
- 不要允许前端直接修改 `orders.status`。
- 不要允许前端直接删除帖子、评论、订单。
- 不要把管理端能力只藏在页面入口里，后端也必须校验角色。
